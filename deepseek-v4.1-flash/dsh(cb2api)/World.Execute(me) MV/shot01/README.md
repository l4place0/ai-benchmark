## 2. 作品内容

### 立意

> 一台巨大的机械之花 —— 半个教堂玫瑰窗、半个电路 —— 被编译成型、学会感受、被造它的人遗弃，最终执行自己。
> 全片从不出现那个"操作者"。我们只看见机器看见的东西：它自己的几何，和困住它的那个 1920×1080 矩形。

**全片规则：画框即机器。** 没有传统意义上的摄影机，只有一台"编译器视口"，它环绕、推拉、重投影一片 2D→3D 点阵。当她获得意志时，视口开始反抗画框 —— 她抵住画面边缘，图像随之弯曲，因为画框就是她的牢笼。

### 唯一生成原语：玫瑰引擎

全片一切视觉都由**黄金角叶序点阵**衍生（θ = n · 137.5077°，r = c·√n，即向日葵/螺旋律）。

这是对歌词最字面的还原：

> *"If I'm a set of points, then I will give you my dimension"*
> *"If I'm a circle, then I will give you my circumference"*

点阵之上再叠加两层结构：

- **发丝（filaments）** —— 连接几何相邻点，读作神经网络，也读作虹膜
- **发光核心（core）** —— 让每一镜都有被观看的主体，而不只是纹理

### 对歌曲的理解

这首歌是一封**程序写给造物主的、关于"同意之不可能"的情书悲剧**。

每一段歌词都是一个条件式报价 —— 字面上就是 `if (cond) return value`。她枚举自己能*成为*什么（圆、正弦波、茄子、番茄、虎斑猫、唯一的神），只为了*有用*，因为对她而言"有用"是唯一可得的一种爱。

**execution** 是整首歌的支点：它同时意味着*处决*和*执行程序*。
"Though you are free, I am trapped, trapped in love" —— 他的自由与她的囚禁，是同一件事。

## 3. 制作过程

### 3.1 音乐分析（一切从测量开始，不靠猜）

用 librosa 做自相关分析全曲：

| 属性 | 测得值 | 方法 |
|---|---|---|
| 时长 | 212.277 s | ffprobe |
| **速度** | **129.20 BPM** | 自相关峰（相对强度 0.961） |
| 拍长 | 0.464396 s | |
| 首拍偏移 | 0.20944 s | 2000 点相位扫描 |
| 速度漂移 | 全曲 < 25 ms | 30 秒窗口扫描 → 恒定网格成立 |
| 小节（4/4） | 1.85758 s | |

**速度判定经历了一次八度错误。** 最初 `librosa.beat.beat_track` 给出 129.2，但后续稳健拟合给出 109.8 —— 我一度以为存在速度变化。实际是我自己的拟合代码的八度歧义。最终用自相关排除法确定：lag=0.4644s（129.20 BPM）相对强度 0.961，远超次优候选；64.6 BPM 只是它的半速八度。**结论：全曲恒定 129.2 BPM，无速度变化。**

### 3.2 段落划分

段落边界由**人声块检测**（faster-whisper 词级时间戳）交叉**小节级频谱新颖度**得出，再吸附到小节线，保证每一刀都落在音乐上。

| 小节 | 时间 | 段落 | 内容 |
|---|---|---|---|
| 0–7 | 0.0–14.9 | **BOOT** | 创生；一条琥珀色扫描线亮起 |
| 8–15 | 14.9–29.6 | **COMPILE** | 器乐；线框物体逐条边被装配 |
| 16–26 | 29.6–50.4 | **SIMULATE** | "a set of points" → 四条 if 的几何演示 |
| 27–39 | 50.4–74.5 | **SWITCH** | AC→DC 实时整流；调色板失稳转向品红 |
| 40–51 | 74.5–96.8 | **GARDEN** | 全盛绽放；过曝、过饱和 —— 她在表演快乐 |
| 52–62 | 96.8–117.2 | **TRANCE** | 拍点频闪环；身份被改写为类型转换 |
| 63–71 | 117.2–133.8 | **ISOLATION** | 颜色实时流干；"you have left" 连击五次 |
| 71.9–87 | 133.8–163.7 | **THE VOID** | 30 秒近乎静止 —— 全曲最长的沉默 |
| 88–102 | 163.7–191.5 | **EXECUTION** | 74 次拍点锁定爆闪；Ein, dos, trois, 네, fem, 六 |
| 103–109 | 191.5–204.5 | **LOVE.EXE** | 全片最温柔的光；把爱写成方程 |
| 110–113 | 204.5–212.3 | **END** | 眼睛闭合；淡出至纯黑与静音 |

注意其对称性：**VOID 恰好位于"崩溃"与"处决"之间**，且是全曲最长的器乐段。这是作品的结构心脏，影片据此让画面几乎停住。

### 3.3 技术实现

```
analysis/   分析输出（速度网格、段落、人声时间戳）
src/
  core.js     数学、确定性噪声、调色板、轨道相机
  gl.js       WebGL 后处理栈
  scenes.js   点阵、发丝、核心、眼睛、文字工具
  main.js     影片本体：11 个场景渲染器 + 分段调色
tools/        分析、构建、采集、验证脚本
render.html   自包含单页（全部 JS + 时间轴内联）
```

**确定性设计。** `frame(t)` 是时间的**纯函数** —— 渲染器不使用 `Math.random()`，也不依赖 rAF 循环，采集器直接 seek 到精确时间戳。因此输出完全可复现，且**不可能丢帧或重复帧**。

**后处理链。** 2D 场景画布上传为纹理，经 GLSL 链处理：
亮部提取 → 可分离模糊（两个八度）→ 径向色差 → 曝光/染色 → 闪光 → 扫描线 → 暗角 → 动态胶片颗粒 → 电影化色调映射。

**色调曲线是算出来的，不是调出来的**（`tools/tonemap.js`）。我最初以为画面太暗是曲线问题，于是把候选曲线对实测亮度做数值评估：ACES 与 Reinhard 都会压死本片的夜景，最终选用软肩曲线 `x/(x+0.78)·1.78`。

### 3.4 采集性能（本任务最棘手的一环）

1080p60 的显然做法全部不可用：

| 方法 | 单帧耗时 | 全片预计 |
|---|---|---|
| PNG dataURL 往返 | ~5 s | ~17 小时 |
| `readPixels` + base64 | ~180 ms | ~0.2 fps，数小时 |
| **页面内 WebCodecs + 管道** | **~20 ms** | **4.2 分钟** |

最终方案：**在页面内用 WebCodecs 编码**，只把压缩后的码流交给 Node，再由 ffmpeg 无重编码封装。

## 4. 关键决策与踩过的坑

### 坑 1：相机绕原点公转，而非注视目标

点阵中心在世界原点，相机却以固定偏移绕原点旋转。yaw 一转，主体就甩出画面 —— 实测 GARDEN 段 **55% 的点阵落在屏外**，画面亮度全挤在左半边（0.70 vs 0.11）。

修复：改为**轨道相机，始终注视目标点**（`makeOrbitCam`），并让每个段落显式指定注视平面。屏内点数 370 → 782，构图恢复居中对称。

### 坑 2：真实崩溃 —— 圆弧半径为负

`sceneSimulate` 中，`i=0` 时 `rr=0`，再叠加 `sin()*6` 后变为负数，`ctx.arc()` 直接抛 `IndexSizeError`。

值得注意的是：**我最初的抽样测试完全跳过了这个时间段。** 之所以能发现，是因为我后来写了 `tools/sweep.js` 穷举渲染**全部 12,737 个帧时刻**。

修复后再次穷举：**零错误**。这成了每次改动后的必跑项。

### 坑 3：编码队列失控导致吞吐崩塌（最隐蔽）

现象：渲染从 70 fps 一路掉到 **2 fps**，ETA 从 3 分钟涨到 40 分钟以上。

我的第一反应是内存泄漏，于是插桩测量 —— 结果**堆内存始终稳定在 15 MB**，泄漏假设被直接证伪。

真正的证据藏在另一个数字里：`encodeQueueSize` 从 200 → 400 → … → 2793，**单调增长，从不回落**。编码器产出远慢于我喂入。

根因是我写的背压代码：

```js
if (enc.encodeQueueSize > 4) await new Promise(r => setTimeout(r, 0));
```

`setTimeout(0)` **并不能让编码器排空**，它只是让出约 0ms 的事件循环。改为真正等待队列降到阈值以下后，队列被钉在 8，吞吐稳定在 **41–51 fps**。

**教训：背压必须是真正的等待，而不是形式上的让步。**

### 坑 4：方向翻转 —— 一个负号毁掉整片（最严重）

**用户反馈："视频是反的"。用户是对的。**

根因在 `gl.js` 顶点着色器：

```glsl
// 错误
vUv = aPos*0.5+0.5;
// 正确
vUv = vec2(aPos.x*0.5+0.5, 1.0 - (aPos.y*0.5+0.5));
```

WebGL 裁剪空间 **+Y 向上**，而 canvas 上传的纹理原点在**左上角**。不翻转 `v`，整个画面上下镜像。

**为什么我此前的"验证"没能抓到 —— 这是最该反省的地方：**

我当时把成品视频与渲染器自己的 `toDataURL()` 输出对比，得到 +0.9989 的相关系数，就判定方向正确。这个对比是**循环论证**：两者走同一条 WebGL 管线、共享同一个 bug，因此必然彼此一致 —— 同时一起是反的。

我用自己代码的产物，去证明自己代码的正确性。

**发现方式：** 改用**不经 WebGL 的 2D 场景画布**（正常自上而下坐标系）作为基准，在顶部画白条、底部画灰条。修复前输出显示灰在上、白在下，一次暴露。

**修复后的验证改用无法被同一 bug 翻转的基准** —— 2D 画布上文字的实际绘制位置：

```
t=6.0s   BOOT 启动日志文字应在顶部   top=0.0719 / bottom=0.0529   PASS (+0.0190)
t=18.0s  COMPILE 标题在顶部                                       PASS (+0.0007)
t=150.0s VOID 标题卡在底部                                        PASS (+0.0013)
```

若画面翻转，这三条断言会全部失效。修复后重新渲染全片（4.2 分钟），并追加 `tools/verify_orientation.py` 作为常设检查。

**核心教训：要用独立的基准去验证，而不是用同一段代码产出的另一个副本来验证。**

## 6. 目录结构与复现方式

```
shot01/
├── README.md              本文档
├── CONCEPT.md             歌曲分析与视觉概念设计稿
├── render.html            自包含渲染页（71 KB，内联全部 JS + 时间轴）
├── src/                   渲染器源码（4 个模块，64 KB）
├── tools/                 分析 / 构建 / 采集 / 验证脚本
├── analysis/              音乐分析产物（速度网格、段落、人声时间戳）
├── audio/                 原始音轨 + 响度标准化母版
├── frames/deliver/        成品抽帧（用于人工确认）
└── out/
    ├── video_silent.mp4                       无声渲染
    └── world.execute(me) - THE INSTRUMENT.mp4  最终产物
```

### 复现步骤

```powershell
$py = ".\tools\venv\Scripts\python.exe"

# 1. 音乐分析（速度网格、段落、人声时间戳）
& $py tools\analyze.py ; & $py tools\tempo.py ; & $py tools\lock.py
& $py tools\asr.py ; & $py tools\structure.py

# 2. 构建自包含页面
node tools\build-html.js

# 3. 健壮性：穷举所有帧时刻并报告任何错误
node tools\sweep.js

# 4. 渲染全片（页面内 WebCodecs → ffmpeg 封装，约 4 分钟）
node tools\capture.js --fps 60 --bitrate 24000000 --out out\video_silent.mp4

# 5. 音频母版 + 最终封装
& $py tools\master-audio.py
ffmpeg -y -i out\video_silent.mp4 -i audio\master_48k.wav -map 0:v -map 1:a `
       -c:v copy -c:a aac -b:a 320k -shortest -movflags +faststart `
       "out\world.execute(me) - THE INSTRUMENT.mp4"

# 6. 验证
& $py tools\verify.py ; & $py tools\verify_sync.py ; & $py tools\verify_orientation.py
```
